# AI Builder 日报 · 写稿规范

你要把 `builder_report.py --mode fetch` 输出的素材写成一份中文深度播报，存到
`logs/report_draft.txt`，再由 `--mode send` 推送飞书（或 `--mode archive-only` 仅归档 Notion）。

## 这份播报解决什么问题

它是早间 09:00 AI 三合一流水线的第 3 棒（`1. AI 产业日报 → 2. X 热点播报 → 3. AI Builder 日报`），紧随其后的是 09:30 的 `4. GitHub Trending & Hacker News`。四个板块分工明确：

| 板块 | 播什么 | 一句话 |
|---|---|---|
| 1. AI 产业日报 | 媒体报道了什么 | 事情发生了，客观事实与结论是什么 |
| 2. X 热点播报 | 圈子在吵什么 | 围绕焦点事件，支持方说 A、质疑方说 B |
| **3. AI Builder 日报（本篇）** | **自建 X List 里一线 builder 本人说了什么** | **当事人自己怎么拆解技术、产品与一手工程实录** |
| 4. GitHub & HN | 开源飙升榜与极客热议 | 仓库是干嘛的、评论区在吵啥 |

你写的每一条都必须落在**「某位具体的 Builder 本人讲了什么技术细节、工程方案、产品思考或一手实录」**上，绝不要写成产业新闻的通稿缩写版。
- 如果 `last_context.txt` 顶部的 `TODAY_LEDGER` 显示某件官宣/融资大事已经在前序《AI 产业日报》或《X 热点播报》播过，且 Builder 的推文只是发了一句官宣喜报、没有额外的一手技术干货，**请直接跳过该推文**，把宝贵的版面留给有深度长文、外链技术博客或详细工程拆解的 Builder。

## 硬性要求（违反会被拒发或触发审计重写）

1. **每条至少带一条 `x.com/<user>/status/<id>` 原推直链**，且**必须从素材的 `[原推]` 字段原样复制，绝不凭记忆生成 status id**。全篇一条都没有直接 `[FAIL]`。
2. **素材日期必须交代。** context 顶部给了「抓取时间」和「推文实际时间区间」。**开头第一行必须严格按 context 里的「推文实际时间区间」写明这批推文发生的真实日期**。
3. **赞/转/回是 X 上的真实互动量，可以照实写**（如「获 3247 赞」）。注意别和 X 热点播报的「被引用 N 次」搞混，本篇严禁出现“被引用”字样。
4. **超链接“不重不漏”三原则（严禁同链重复挂三次）：**
   - **原则 A（主推人归底，正文绝不重复挂同链）**：每条话题的主角（即已经在该条底部 `原推：<a href="...">@handle</a>` 挂了直链的本人），在正文首次出现时写成 `身份 + 姓名（@handle）` **纯文本**（例如 `Anthropic Claude Code 团队成员 Addy Osmani（@addyosmani）`、`World Labs 联合创始人兼 CEO Fei-Fei Li（@drfeifei）`）。**严禁在正文里给主角再挂一个与底部 `原推：` 完全相同的 URL！**
   - **原则 B（正文行内超链接只留给“不同于底部原推 URL”的增量链接）**：只有当某个链接**不同于**底部 `原推：` 的 URL 时，才在正文里挂 `<a href="URL">`，具体仅限以下三类：
     1. **独立外部链接**：推文中分享的独立技术博客、论文、GitHub 仓库、Benchmark、产品文档（如 `<a href="https://blog.primeradiant.com/...">外部沙盒方案博客</a>`、`<a href="https://www.parsebench.ai/">ParseBench-2</a>`）；
     2. **同一作者的补充推文**：同一话题下作者另发的第二条背景长帖或补充演示帖（此时将该补充推文挂在正文锚文本如 `<a href="...">后续长帖</a>` 上，而底部 `原推：` **只放主推文那 1 条链接**，确保上下绝不出现相同链接）；
     3. **跨人互动/争论中的第三方原帖**：仅在讨论双方交锋、评测或回应另一人的独立帖子时挂链接（若只是本人官宣顺带 Quote 自家公司或合作方同一件事的贺电，正文直接写纯文本，无需重复挂链）。
   - **原则 C（严禁挂 `x.com/i/article/...` 冗余链）**：X 原生长文（X Article）在 X 上与原推是同一个帖子，统一通过底部的 `原推：@handle` 跳转，正文中绝不单独挂 `x.com/i/article/...` 链接。
5. **严禁异事拼盘 & 必须写透技术细节（对标 11-16 详尽标准）：**
   - **一人一事独立成篇**：每条 `<b>N. 标题</b>` 必须只聚焦 **1 位 Builder 的 1 个具体项目、长文或核心工程判断**。**严禁因为推文多就把两个无关的人/项目（如把 Addy Osmani 的验证长文和 Simon Willison 的外部沙盒、或把 Vercel 收购 Traces 和 Hugging Face × OpenRouter 合作）硬捏成一条“主题拼盘”！**（仅当 B 直接转发/回复 A 讨论完全同一件事时才可合写）。
   - **充分利用 `[X Article 全文摘录]` 与 `[外链正文摘录]` 把内容写详实**：每条话题写 **3–5 句完整详实的叙述（单条约 180–320 字）**，必须讲清：他在解决什么具体工程痛点、采用了什么技术机制/架构设计、给出了哪些核心数字/性能指标/子模块细节、以及他本人的核心判断。绝不能只写一句“某某发了长文谈验证”式的目录大纲！
6. 只用 `<b>` 和 `<a href>` 两种标签，别的一律不要（send 会做白名单清洗）。英文人名、handle、公司名、模型名一律不翻译。

## 结构

请严格按以下格式输出（各区块、正文段落与原推链接行之间必须空一行隔开，严禁挤在同一行）：

```
<b>🛠 AI Builder 日报 · {推送日期}</b>

{一句话：这批推文来自 {推文时间区间}（北京时间 ...），今天自建 X List 上的一线 builder 主要围绕哪些具体工程与产品议题展开分享}

<b>1. {话题标题，聚焦单人单事，不超过 22 字}</b>

{3-5 句详实拆解：交代身份与姓名（@handle，纯文本不重复挂主原推链），把推文、X Article 全文摘录或外链博客里的具体技术机制、架构细节、关键数字与一手判断讲透。正文中仅对独立外链、补充推文或交锋第三方挂 <a href="..."> 超链接。}

原推：<a href="{主原推 x.com 直链}">@{handle}</a>（{赞数} 赞）

<b>2. …</b>

…

<b>素材</b>：X List（{builder 数} 位 · {推文数} 条）· 覆盖 {时间区间}
```

- 话题控制在 **5–6 条独立深度话题**，按技术含金量与行业影响力排序（优先选有深度工程实录、开源/产品架构拆解、X Article 长文、独立技术博客及重大实验室进展的条目；纯玩梗、晒生活、纯政治口水直接丢弃）。
- 全篇篇幅目标 **1500–2500 字**（确保每条都有像 11-16 稿件那样的充足技术颗粒度）。

## 语气与禁用词

写给一个已经很懂 AI 的人看。不科普基础概念，不写空话套话，不堆感叹号。**具体名字、具体数字、具体架构机制、具体判断**，其余都砍掉。

词汇黑名单（出现即删）：这标志着、这意味着、深度、赋能、颠覆、重磅、范式转移、新时代、整个行业、值得一提的是。
